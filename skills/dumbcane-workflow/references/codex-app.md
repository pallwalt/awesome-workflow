# Codex desktop App adaptation

Read when selecting tools, delegation or workspace behavior. The actual host interface and higher-priority instructions govern. This file is guidance, not a declaration that every App version exposes the same tools.

## Capability check

Check only capabilities needed for the next authorized action.

| Capability | When needed | If unavailable |
| --- | --- | --- |
| Read project and skill files | Investigation and provider discovery | Request the specific missing source or access; do not invent its contents. |
| Write files | Authorized implementation or saved deliverable | Deliver the permitted analysis; identify implementation as unavailable. |
| Execute local commands | Build, tests or runtime checks | Use an equivalent inspection where sufficient; otherwise keep the affected verification unverified. |
| Superpowers method files | Before their corresponding phases | Follow [compatibility](superpowers-compatibility.md); this required dependency has no invented built-in replacement. |
| Git inspection | Existing Git projects and topology decisions | Use available file evidence; do not initialize Git merely to satisfy the workflow. |
| Native subagents | Useful bounded delegation | Use a supported inline method. Do not create a sidebar chat as an internal subagent substitute. |
| Browser/runtime inspection | Acceptance requires rendered UI or interaction evidence | Use an allowed equivalent, or report the unverified UI behavior. Passing a build is insufficient. |
| Network or external services | The authorized task actually needs them | Continue independent local work and identify the exact missing prerequisite. |

Load exact catalog names when a skill interface exists. When the host instructs skills to be read from disk, read the actual file and apply it; report that mechanism accurately. Never fabricate a `Skill`, `AgentSwarm`, plan-mode or approval parameter.

## Workspace and user work

Consume the controller's task-scoped workspace contract. Inspect current relevant edits before implementation. Distinguish linked worktrees, host-managed checkouts and submodules; a different Git common directory alone is not enough to identify a linked worktree.

Prefer host-managed lifecycle tools for an authorized host-managed workspace. The existence of such a tool is not consent to create a worktree. Never globally reset or clean to obtain a passing baseline. Record relevant baseline failures separately from regressions.

## Delegation and long-running commands

Use the live dispatch, follow-up and wait interfaces. A running-session identifier means resume the command using that interface, not start another copy. Do independent work while waiting, or use a bounded wait compatible with host responsiveness rules.

Inherit model settings unless an actual user or applicable instruction authorizes an override. Do not change App settings or install a plugin to satisfy a preferred execution method.

## Owned resources

Record servers, browser sessions and processes started for this task, including their identifiers and owner. Close those resources after verification, failure or cancellation when no longer needed, and confirm they exited. Do not kill processes by global name or touch a user's browser profile.

Use one browser execution slot by default and respect stricter project or host limits. Other useful read-only work may proceed independently. A fixture requiring only HTTP API behavior needs HTTP tests, not a browser claim.

## Installation and support claims

The repository source is separate from the installed skill. The managed installer in this package creates one discoverable Dumbcane entry and keeps the pinned official provider beside the installed package. It refuses an entry owned by another installation. Read the installed provider by its physical path; do not substitute a global same-named method. Reading a source candidate by absolute path during an agent trial is not an App discovery or clean-install test. Do not replace existing skills or register a plugin without authorization for that action.

For a clean App discovery trial, use a dedicated test environment, record the App version, model, installed provider identity and observed invocation. Do not reset or restart the user's active workspace to simulate a clean machine. Filesystem lifecycle tests can pass while App discovery remains unverified; report those separately.
